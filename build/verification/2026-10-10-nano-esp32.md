# 0.10.0, the Arduino Nano ESP32 image: what ran, and on which bytes

## What this release is

The image rebranded for the Arduino Nano ESP32, with the two services the
board never used removed and the flash recut so `/home` is 5.00 MiB instead
of 3.25 MiB. The partition offsets moved, so a board carrying the previous
table must be flashed with the whole combined image, not with `--parts`.
[CHANGELOG.md](../../CHANGELOG.md) has the full list of changes; this record
is only what was measured and on what.

## The image, and where it came from

`build/reproduce-macos.sh` built the working tree on an Apple Silicon Mac
inside the pinned amd64 container, and `make-images.sh` assembled the result
into `images/`. The combined image the suites ran on:

```
1feff1907a94e73296534b7057c32a1d1b3bf7a1747fe6725a0c1fec6718c644  linux-esp32s3-native-full.bin
```

Every file in `images/` is byte-identical to `build-output/reproduce.macos/
artifacts/`, so the flashable release and the build output are the same
bytes. The build recorded its source as `b8977c8-dirty`: the correction pass
that followed the rebrand commit had not been committed when the image was
built. Four files under `rootfs_overlay/` were edited afterwards — the
comments in `usr/sbin/bootlog` and `etc/init.d/S00bootlog`, the
`BOOTLOG_CMDLINE`/`BOOTLOG_LEVEL` and `LOWMEM_MEMINFO` test seams, and one
`bootlog status` message string. They were compared by extracting them from
the shipped cramfs and diffing, not by timestamp, and none of them changes
what the board does.

## The suite

`build/test-board.py`, over the UART console, on the image hash above:
**35 tests, 0 failed**. MemAvailable at the start of the suite is 4312 kB of
7852 kB. A 256 KiB jffs2 write takes 3 s.

The suite covers, among the rest: the boot, the installed kernel and rootfs
hashes read back off the flash partitions, the MMU executable remap, the
fork suites static and dynamic, the process suite, Bash, Dash, Make,
MicroPython, the network tools, the job queue, the three `bootlog` checks,
the hardware RSA accelerator, the memory baseline, and the kernel health at
the end.

## The extra checks

`build/extra-board-tests.py`: **13 of 13**. Detached session attach, cron,
`passwd` and re-login, a reboot with `/home` persisting, the RGB LED dark at
boot, `neofetch` reading the board, the bank latch silent after a load, shell
pipelines and subshells, exec arguments fitting the stack, a jffs2 write
copied and read back, the swap model, and the kernel health at the end.

`bootlog-across-reboots` failed on its first run against these bytes and
passed on the second. The failure was in the test, not the image: it asserted
that `bootlog quiet` would make the *next* boot quieter, which nothing
running after the kernel can do — the kernel writes its whole log before any
script runs. The test was rewritten to assert what the design guarantees, and
the wording in `bootlog` was corrected to say the same thing. That is the
test-seam and message part of the four-file difference above.

## What did not run

- The 20-cold-boot soak (`build/soak-boot.py`). 0.9.1 remains the last
  release with a soak behind it.
- The SSH, Telnet and network-service tests. They need WiFi credentials, and
  a fresh image has none configured.
- The factory first-login test — it wants a board with factory `/etc` and
  `/home`.
- The board was flashed over its own USB port through a hand-entered download
  mode, because an Arduino Nano ESP32 cannot be reset into the bootloader
  from that port by esptool alone. That is a property of the board, and
  `flash.sh --before no_reset` documents it.

## What was seen by eye

- The LED is dark at boot and the blue channel lights when driven low, which
  is what active-low means on this part.
- The boot streams live at `CONFIG_CONSOLE_LOGLEVEL_DEFAULT=7` with no
  `quiet` on the command line, and `bootlog verbose` adds `KERN_DEBUG`.
- The banner prints the art, the `uname` line and `Last login:`; the prompt
  reads `root@arduino-nano-esp32:~#`.
- `espsta0` comes up with a DHCP address, so the removal of BLE and the web
  server did not disturb the network path.
